# Experience boost — implementable effect spec (v2, decision-owner directive)

Supersedes the "one signature moment" restraint of `02-experience-vision.md` §2 for this pass only: the decision-owner explicitly asked for more interactivity, more effects, animation across the whole site. Constraints are unchanged and non-negotiable: compositor-only (`transform`/`opacity`/`clip-path`/`filter`), no libraries, total hand-written JS ≤ 25 KB, no 3D/WebGL, no custom cursor, no sound, no scroll-jacking, everything zeroed under `prefers-reduced-motion`, nothing content-bearing hidden without JS. All new tokens extend `motion-tokens.css`; no ad hoc durations/easings.

## New tokens (add to `motion-tokens.css`)
`--motion-slower: 900ms` (draw-in effects), `--ease-out-soft: cubic-bezier(0.16,1,0.3,1)` (counters, FLIP), `--parallax-max: 12px` (hero photo cap), `--tilt-max: 4deg` (card tilt cap), `--magnetic-max: 4px`.

## Header
1. **Compact on scroll** (existing) — keep as-is.
2. **CTA bar entrance** (existing) — keep as-is.
3. **NEW — nav underline draw**: trigger scroll-spy change; `clip-path: inset(0 100% 0 0)` → `inset(0 0 0 0)` under active link, `--motion-fast` / `--ease-firm`. Fallback: `aria-current` colour change only, no clip-path. Why: makes wayfinding legible as movement, costs one property, no JS beyond existing IO.

## Hero
1. **Headline word-reveal**: split headline into `<span>` per word at build time (static markup, no runtime split JS); each span `clip-path: inset(0 0 100% 0)` → `inset(0 0 0% 0)`, `--stagger-step` per word capped at 6 (cap already defined), `--motion-base`/`--ease-steady`. Fires once on load, not on scroll. Why: reinforces reading order the way the existing lead/CTA stagger already does, one step more granular; clip-path avoids layout/paint cost of animating font metrics.
2. **Photo parallax-lite**: `transform: translateY()` on `.ridge img` only, driven by IntersectionObserver (attaches rAF loop only while `.ridge` is in viewport, detaches on exit) — never a permanent scroll listener. Cap at `--parallax-max` (12px), `--ease-linear`. Fallback: static image, no transform, IO unsupported → `no-js`/reduced-motion class skips it entirely. Why: was explicitly rejected in v1 for being ungated continuous cost; the IO-gated version removes that cost (listener only runs ~1–2s while hero is on screen), keeping the brand's "steady" read while answering the boost request.
3. **Stat counters**: `Est 2024 / 12 mo / 30 days` — "12" and "30" count up from 0 on first viewport entry via `requestAnimationFrame`, `--motion-slow` (700ms), `--ease-out-soft`, driven by `textContent`, not transform (numerals are not compositor-eligible but the animation is short, one-shot, IO-gated, and touches 2 text nodes — negligible layout cost). "Est 2024" and unit labels do not count (no meaningful zero-state). Fallback: final numbers render immediately, no-JS/reduced-motion. Why: turns credibility stats into a noticed moment without touching layout-affecting properties elsewhere.

## Ridgeline mark (divider motif)
1. **Stroke-draw on load**: if the ridgeline mark is (or becomes) inline SVG, animate `stroke-dashoffset` (paint-only, not layout) from path length to 0 once on load, `--motion-slower` (900ms), `--ease-steady`. Used both as brand mark and as a thin horizontal ridge-profile divider between 2–3 major sections (services→process, about→work). Fallback: mark renders fully drawn, static line divider if not SVG. Why: gives the brand mark one authored moment and reuses it structurally as a divider motif instead of inventing a new decorative element — one idea, two placements, no extra JS (CSS `@keyframes` on page load, no scroll trigger, no listener).

## Services cards
1. **Tilt-lite on hover** (desktop/pointer:fine only): `transform: perspective(600px) rotateX() rotateY()` mapped from pointer position within card bounds, capped at `--tilt-max` (4deg), `--motion-fast`, compositor-only. Icon inside gets an independent `translateY(-2px)` on the same hover. Fallback: existing surface-swap hover only; `@media (hover:hover) and (pointer:fine)` gates it, touch gets plain tap-through. Why: reads as "more effects" while staying under the shadow-free, compositor-only rule; capped angle keeps it a wink, not a gimmick.
2. **Reveal + stagger** (existing) — keep.

## Process (How we work)
1. **Stagger reveal** (existing) — keep.
2. **NEW — connecting progress line**: a single absolutely-positioned line/rail behind the step numbers; its "filled" portion is one pseudo-element with `transform: scaleY()` (transform-origin top), driven by the same per-step IO entries already firing stagger — each step crossing viewport bumps the fill to that step's offset. No continuous scroll listener: fill only updates on IO threshold crossings (max 4 state changes for 4 steps), `--motion-base`/`--ease-steady`. Fallback: full line renders solid immediately, no scale transform, under reduced-motion or no-JS. Why: answers the "connect the steps" idea from the brief without resurrecting the scroll-linked progress bar rejected in `03-motion-spec.md` — this is IO-event-driven, not scroll-position-driven, so it's cheap and matches the "no continuous listener" rule.

## About
1. **Portrait clip-reveal**: `.portrait img` clip-path wipe (`inset(0 0 0 0)` from `inset(0 0 100% 0)`) on scroll-into-view, `--motion-base`/`--ease-steady`, once. Replaces plain `.reveal` fade for this one image only. Fallback: image visible immediately, no clip-path, reduced-motion/no-JS.
2. **Avatar ring**: a static ring already implied by brand mark reuse — animate its `stroke-dashoffset` (if SVG ring) same technique as the divider mark, on the same IO trigger as the portrait wipe, `--motion-base`, so both fire together as one visual "beat," not two competing motions. Fallback: full ring, static. Why: two effects here are treated as one choreographed moment (same trigger, same duration) to respect the "one movement per viewport" choreography rule from `03-motion-spec.md` even while adding more effects overall.

## Recent work
1. **Duotone-to-colour hover**: `.tile--duo img` `filter: grayscale(1) contrast(1.05)` → `grayscale(0) contrast(1)` on hover/focus, `--motion-base`/`--ease-firm`, filter is compositor/GPU-cheap for a single image layer. Caption (`.cap`) gets `transform: translateY(8px)→0` + opacity on the same trigger. Fallback: hover states have no touch equivalent (per v1's accepted trade-off) — touch users get full-colour + caption always visible via a `@media (hover:none)` rule, so nothing is hidden without pointer capability.
2. **Category filter with FLIP**: three filter chips (Landscape/Carpentry/Build/All) toggle a `data-cat` filter; hidden tiles get `opacity:0; transform:scale(.96); pointer-events:none` (removed from tab order via `inert` or `tabindex=-1`, not `display:none`, to keep the FLIP measurement stable) and remaining tiles reflow via a small FLIP module: measure old rects, apply new grid position, invert with `transform`, then transition `transform` back to none, `--motion-base`/`--ease-out-soft`. This is the single largest JS addition — budgeted at ≤ 6 KB. Fallback: no-JS shows all tiles ungrouped with visible category labels already on each tile (the label is content, not JS-dependent); reduced-motion applies the filter instantly with no invert/transition step.
3. **Stagger reveal** (existing, on initial load only) — keep.

## FAQ
1. **Animated disclosure via grid-rows**: replace/augment native `<details>` with `<button aria-expanded>` + panel using `grid-template-rows: 0fr → 1fr` on the panel wrapper (the one animatable-height technique that avoids `height:auto` jank and stays out of layout-thrash territory since it's a single grid track, not a measured scrollHeight loop), `--motion-base`/`--ease-steady`. Must remain a real `<button>`/`aria-expanded` pair, not a repurposed `<details>`, to keep the animation controllable. Fallback: if JS absent, ship plain `<details>/<summary>` markup instead (progressive enhancement swap at template level, not a broken button) — reduced-motion sets `grid-template-rows` transition to none, panel snaps open/closed instantly. Why: this is the one place the brief's "more effects" directly trades against the v1 "native and free" argument — accepted because grid-rows keeps the cost near-zero (one property, no JS height measurement) while giving the section a visible animation the current `<details>` default cannot.

## Contact form
1. **Floating labels**: label `transform: translateY()` + `font-size` shift on `:focus`/`:not(:placeholder-shown)`, pure CSS, `--motion-fast`. Fallback: none needed, CSS-only, degrades to static label if unsupported (progressive, not a fallback branch).
2. **Button loading/success state**: on submit, button gets `data-state="loading"` (spinner via `transform: rotate()` on a small pseudo-element, `animation` looping only while loading — must be paused/removed on response, never an infinite decorative loop) then `data-state="success"` (checkmark via `stroke-dashoffset` draw, one-shot, `--motion-base`). Text fallback (existing `status` `aria-live` region) remains the source of truth for screen readers; the animation is decorative on top of it, not a replacement. Fallback: reduced-motion shows state changes as instant colour/icon swaps, no rotate/draw.

## Footer / cross-section
1. **Marquee strip**: "Landscape · Carpentry · Build · Waiheke" looping horizontally between two sections (e.g. services→process or work→FAQ), pure CSS `@keyframes` `transform: translateX()` on a duplicated content track (standard seamless-loop pattern), `animation-play-state: paused` under reduced-motion (text remains readable, static, wraps normally — not clipped mid-loop). No JS. Why: cheap, on-brand repetition of the three service categories + location, reinforces the offering between content sections without demanding attention (opacity/colour kept low-contrast, decorative, `aria-hidden="true"` since the same words exist as real content elsewhere).
2. **Magnetic-lite buttons**: primary CTA buttons get pointer-tracked `translate()` capped at `--magnetic-max` (4px) on `pointermove` within a padded hit area, released to `translate(0)` with `--motion-fast` on leave. Desktop/pointer:fine only, same media gate as card tilt. Why requested explicitly; capped tightly (4px) to stay "lite" per the brief's own naming, no risk of misclick.
3. **Ripple on press**: `::after` pseudo-element `transform: scale()` + `opacity` fade from press origin (CSS custom properties `--x`/`--y` set via one small JS listener on `pointerdown`), `--motion-fast`, compositor-only. Fallback: `:active` colour change only, reduced-motion/no-JS. Why: satisfies "more effects" on the highest-traffic touch target (buttons) at near-zero JS cost (~1 KB: set two CSS vars on pointerdown).

## Performance budget (revised)
- **JS total ≤ 25 KB** hand-written, uncompressed: existing menu/scroll-spy/reveal/form (~6 KB, per v1) + FLIP filter module (≤6 KB) + hero parallax IO+rAF (≤2 KB) + counters (≤1 KB) + process progress-line IO hook (≤1.5 KB) + magnetic/ripple/tilt pointer handlers (≤2.5 KB) + button loading/success state (≤1 KB) + floating-label/grid-rows FAQ toggle (≤2 KB) ≈ **22 KB**, 3 KB headroom for QA findings.
- **LCP < 2.5s on 4G**: hero image and headline reveal must not block first paint; word-split markup ships pre-rendered (no runtime `split()`), clip-path reveal starts after `load`/first-paint, never gates visibility.
- **CLS 0**: FAQ grid-rows track, FLIP filter, and marquee duplicate track all reserve space up front; FLIP hidden tiles keep their grid cell via `visibility`-safe `opacity`+`pointer-events`, never `display:none`, so no reflow spike.
- **No permanent scroll/pointer listeners**: every effect above is IO-gated (attach only in-viewport, detach on exit) or event-gated (hover/pointermove/pointerdown), matching the "no continuous listener" rule already set in `03-motion-spec.md`. Marquee and mark stroke-draw are pure CSS, zero JS cost.
- **One paint-heavy effect per viewport** still holds informally: hero parallax + stat counters are the only two running simultaneously in the hero, both cheap (one `transform`, one `textContent` write) and IO-scoped to ~1–2s.

## Refused despite the "more effects" request, and why
- **Cursor-follow / trail effects, custom cursor** — explicit out-of-scope in `02-experience-vision.md` §3; adds JS + input latency for zero comprehension gain, and most of this audience is on mobile where cursors don't exist.
- **Continuous scroll-linked progress bars / scroll-jacking / pinned sections** — every "more interactive" idea that requires a persistent `scroll` listener or hijacks native scroll is rejected on the same performance and UX grounds as v1; the process "progress line" above is IO-event-driven specifically to avoid this trap.
- **3D/WebGL hero scene, particle backgrounds, Rive/Lusion-style canvas work** — rejected per existing reference-bar decision; would blow the 4G/low-end-Android budget and contradicts the "person with a nail gun, not a design studio" brand read.
- **Autoplay video/ken-burns on About portrait** — still rejected; the clip-reveal wipe added here is one-shot and stops, not a loop, preserving "this is Pablo speaking" as a still, honest image.
- **Sound on any interaction (button click sound, success chime)** — no exception; unsolicited audio on a jobsite/driving context remains a liability.
- **Infinite/looping decorative animations beyond the marquee** (e.g., a permanently spinning icon, a breathing CTA button) — rejected; anything that loops forever draws attention away from the CTA and fights `prefers-reduced-motion` intent even when "paused," since a paused-but-present loop still needs justification the brief doesn't give.
- **Custom smooth-scroll / scroll-easing library or polyfill** — native scroll stays; overriding it is a common source of jank and accessibility regressions (breaks anchor-jump, find-in-page scroll) for a cosmetic gain not requested specifically.
- **Animating `width`/`height`/`top`/`left` anywhere** (e.g., height-based accordions via `scrollHeight`, animated grid columns) — every height/position animation in this spec uses `clip-path`, `transform`, or `grid-template-rows` (a single-property compositor-friendlier substitute) instead, per the hard constraint; a `scrollHeight`-measuring accordion was considered for FAQ and rejected in favour of the `grid-rows` technique for that reason.

## Gate
All effects above route through `digital-product-team-audit-design`, `digital-product-team-qa-cross-browser`, and `digital-product-team-system-performance` before ship, per standing process; the FLIP filter module and hero parallax are the two items most likely to need JS-size or paint-cost renegotiation and should be reviewed first.
